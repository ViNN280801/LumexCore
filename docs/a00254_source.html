48// Each entry passed to LUMEX_DEFINE_REFLECTED_ENUM is (Name) or (Name, Value), e.g.
49// LUMEX_DEFINE_REFLECTED_ENUM(Foo, std::uint8_t, (A), (B, 5), (C))
50// The wrapping parens make every entry ONE macro argument regardless of an
51// internal comma, so LUMEX_PP_ARG_COUNT below counts entries, not tokens.
52//
53// LUMEX_DEFINE_REFLECTED_ENUM always emits toString(EnumName). Display strings
54// default to the enumerator identifiers (#Name): toString(Foo::B) == "B".
55//
56// Custom strings: do NOT also call LUMEX_DEFINE_REFLECTED_ENUM (that would define
57// toString twice). Use LUMEX_DEFINE_REFLECTED_ENUM_TO_STRING instead:
58// #define FOO_STRINGS(ENTRY) ENTRY(A, "alpha") ENTRY(B, "beta") ENTRY(C, "charlie")
59// LUMEX_DEFINE_REFLECTED_ENUM_TO_STRING(Foo, std::uint8_t, FOO_STRINGS, (A), (B, 5), (C))
60// char const* s = toString(Foo::B); // "beta"
61// There must be no comma between ENTRY(...) entries. Do not name the X-macro
62// parameter after an enumerator (ENTRY(X, "ex") is fine; X(X, "ex") is not:
63// the preprocessor would replace both identifiers). Unlisted enumerators and
64// non-enumerator values of a fixed underlying type return "<Unknown>" (an
65// enumerator can still map to "" explicitly via its own X-macro entry - that
66// is a distinct, deliberate case, not the fallback). The returned pointer is
67// never null.
68//
69// Reflection data is emitted as plain EnumName##Values/First/Size/Last
70// constants next to the enum itself, NOT as an lumex_enum_traits_t<Enum> specialization.
71// Two independent reasons rule that out, both stemming from [temp.expl.spec]
72// (an explicit specialization must be declared in the SAME namespace as its
73// primary template):
74// 1. MSVC (C2888) additionally refuses a lambda inside such a specialization
75// when it is defined inside a namespace - an earlier design built
76// lumex_enum_traits_t<Enum>::values via `[]{ using enum Enum; return std::array{...}; }()`.
77// 2. Even lambda-free, LUMEX_DEFINE_REFLECTED_ENUM is meant to be invoked from
78// inside arbitrary namespaces, or even inside a nested struct/class -
79// neither is the global scope lumex_enum_traits_t<T> would need, so the
80// specialization itself would be ill-formed regardless of what is inside it.
81// `static constexpr` on each generated constant is deliberate: at namespace
82// scope it just gives ordinary internal linkage (harmless per-TU duplication
83// of a few small constexpr values); at class scope it is required for the
84// constant to be a shared class constant rather than a bogus non-static data
85// member. One spelling, both invocation contexts.
